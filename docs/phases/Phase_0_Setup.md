## 0.1 Repository skeleton (DV, day 1)

```
guardrail/
  __init__.py

  taxonomy/ sandbox/ labeling/ models/ detector/ policy/ integration/ eval/

  test_types.py

data/                   # DVC-tracked, gitignored contents
docker/
  Dockerfile
pyproject.toml
Makefile

.github/workflows/ci.yml
```

The website files (`index.html`, `assets/`, `fonts/`) stay at the repo root, untouched.

**`pyproject.toml`**: start with only what Phase 0–2 need. Add dependencies in the phase that first uses them.

```toml
[project]
name = "guardrail"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["numpy", "pyyaml", "jsonschema"]

[project.optional-dependencies]
dev = ["pytest", "ruff", "black", "pre-commit"]

[tool.pytest.ini_options]
testpaths = ["tests"]
```

**`Makefile`**

```make
test:        ; pytest -q
lint:        ; ruff check . && black --check guardrail tests
sandbox-shell: ; docker run --rm -it -v $(PWD):/work guardrail-sandbox bash
```

**CI (`.github/workflows/ci.yml`)**: on push and PR, set up Python 3.11, `pip install -e .[dev]`, then run `make lint test`. Add a `services:` Postgres block only if Phase 2 chooses Postgres for the ledger. SQLite needs nothing.

## 0.2 Docker sandbox image (MG, days 1–2)

```dockerfile
FROM python:3.11-slim
RUN apt-get update && apt-get install -y --no-install-recommends git sqlite3 && rm -rf /var/lib/apt/lists/*
RUN git config --global user.email sandbox@local && git config --global user.name sandbox
WORKDIR /work
```

- Build with `docker build -t guardrail-sandbox docker/`.
- On Windows, run Docker Desktop with the WSL2 backend.
- All sandbox code must also run **without** Docker, using temp dirs, so tests run in CI. Docker exists for isolation when running agent-proposed shell commands (Phase 7–8).

## 0.3 Tracking (DV, day 2)

- **DVC:** `dvc init`; remote on Google Drive (`dvc remote add -d gdrive gdrive://<folder-id>`) or a college server. Track `data/`.
- **MLflow:** `mlflow ui --backend-store-uri ./mlruns` locally. Commit the convention, not the `mlruns/` folder: every training or eval script calls `mlflow.start_run()` and logs its config YAML as an artifact.

## 0.5 Benchmarks: one episode each (MG, days 3–6)

**tau-bench** (Sierra Research):

```bash
git clone https://github.com/sierra-research/tau-bench external/tau-bench
pip install -e external/tau-bench
```

- Run one retail task with the chosen model (see 0.6) and the repo's run script.
- **Record:** where the environment's mutable data lives (the env holds a `data` dict that tools mutate), how tools are defined, and where each task's gold `actions` list sits. Phase 2 and Phase 8 depend on these three facts, so write them into `docs/phases/notes_tau_bench.md`.

**SWE-bench Lite** with a bash-only agent:

```bash
pip install swebench mini-swe-agent
```

- Run **one** Lite instance end to end: the agent proposes bash commands, then the harness evaluates the patch.
- **Record:** the exact place where the agent's command is about to be executed. Phase 7 inserts the gate there. Write it into `notes_swe_bench.md`.

> Verify repository names and entry points when you install. These tools change often, so trust the installed code over this guide.
